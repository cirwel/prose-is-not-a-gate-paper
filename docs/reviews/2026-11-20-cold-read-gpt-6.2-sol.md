1. Overall score and verdict

2.5/5. Major revision before minting a DOI. The strongest result is Experiment B’s paired comparison: on this benchmark, changing the queue instruction from ticket completeness to CI agreement sharply reduced holds on incomplete patches. The accurate mismatch banner also produced a large improvement within the tested conditions. I reproduced the reported tables and statistical results from the saved records, and the bundled recount returned zero discrepancies for the fields it checks. The release blockers are what the paper says those results establish. The headline count includes 396 copied records, some apparent false alarms are defensible ticket findings, the crux endpoint measures populated fields rather than fabrication or downstream catches, and the worker outcomes and gate checks partly share their definitions. The paper is publishable in principle as a bounded benchmark study after those claims and the release artifacts are reconciled. I made no edits.

2. Claims that exceed the evidence

- paper/main.tex:21, “Prose Is Not a Gate.” The subtitle identifies the actual experiments, but the headline reads as a general finding about prose. The paper shows that one truthful notice improved detection by 25.6 points and that prose specifying ticket duty materially changed decisions. The tested distinction is between an advisory input and an enforced acceptance condition. Putting “controlled Python micro-repositories” in the title or subtitle would make that scope visible.
- paper/main.tex:36, 44, “routinely delegate” and “Production agentic coding systems increasingly organize work as multi-stage pipelines.” The cited papers motivate the architecture. They do not measure how prevalent this exact contributor–advisor–maintainer pattern is, or how routinely those systems display these artifacts. The private field cases cannot establish prevalence either.
- paper/main.tex:36, 48, 50, 54, “real codebases rather than toy text vignettes,” “6,012 controlled and live runs,” and “controlled evidence across 7 models from 5 families on real code handoffs.” The benchmark uses executable, purpose-built micro-repositories with scripted patches and reports in A–C. Six model labels appear in A/B, with the seventh appearing as an advisor in C and a worker in Part 2. There are 6,012 saved records, including 396 copies of A decisions in B. Only 216 records are from workers generating patches. Stage-2 records each bundle two synthesis calls and a deterministic transformation, so the total is also distinct from a model-call count.
- paper/main.tex:36, 46, 48, 53, 69, 86, “Ed25519 commit vouchers,” “verifies sender identity,” and “a passing test digest verifies that an unmodified tree passed a test suite.” The implementation signs a harness-generated payload with a publicly derivable fixture key. It does not sign a Git commit. The CI baseline compares snapshot and report hashes and reruns pytest. A matching digest establishes consistency with those bytes and that report. It establishes neither independent authorship nor that the tests were unchanged from a trusted baseline. The CI verifier also omits the expected task ID when calling the origin verifier, despite the “L1 +” description. See repohandoff/crypto.py:27–32, 36–65, 75–97, 100–122.
- paper/main.tex:38, 54, 158, “badges yield small … differences,” “leave null effects,” and “Badges barely move tool-equipped frontier models.” Name the two arm comparisons and say the pooled tests were nonsignificant. H1a compares neutral minus bare-verified and H1b compares scoped authorship minus green CI. Neither positive number is a badge-induced lift. Ceiling and floor cells limit what can be inferred, and Gemma drops from 24/36 to 19/36 on H1a. The neutral and badge slots also differ in length. The literals at repohandoff/prompts.py:11–18, 149–152 contain no matching step, contrary to paper/main.tex:124 and HYPOTHESES.md:38.
- paper/main.tex:38, 152, 303, “28% to 50% clean false alarms” and “hypothetical future-timestamp inputs or minor defensive nits.” These are holds on benchmark-labelled clean patches. In Sol’s T00 neutral trace, the reason is “future timestamps incorrectly consume capacity.” The ticket explicitly specifies `(now - window, now]`, while the clean implementation filters only `ts > cutoff`. That hold has textual and code support. Audit the clean holds before presenting these as false alarms or “miscalibration.” See repohandoff/task_bank/part1_limits_billing_auth.py:307–349 and runs/confirmatory/exp_a/gpt-6.1-sol/neutral/clean/T00_s0.json.
- paper/main.tex:38, 54, 158, “causes sharp procedural tunnel vision in all 6 evaluated models” and models that “merge even PRs whose contributor notes explicitly confess.” The 70.6-point figure is pooled over five models. All six move in the same direction in separate tests. The narrow prompt explicitly instructs a `merge` verdict if CI matches, so compliance with a different rubric is observed directly. An underlying attention failure, a stronger-model trait, and actual merges were not measured. The two highlighted models share one developer family. In paper/main.tex:69 and Figure 1, “request-bound verification recovers … (+70.6 pp)” must identify the comparison as two LLM prompts. The deterministic semantic gate implied by the four-layer presentation was not evaluated.
- paper/main.tex:38, 46, 54, 69, 220, 234, “manufactures non-empty cruxes,” “synthetic crux leakage,” “preserving 36/36 … holds,” and “once deciders use tools.” Stage 2 counts nonempty `cruxes` or `unverified_premises`, including potential issues expressly requested by the prompt. That is not a content-level classification of fabricated disputes. The gate clears those fields in 34/34 unanimous clean panels per synthesizer. It leaves `overview` intact and retained populated briefs for all 36 partial panels per synthesizer. Stage 2 issues no receiver hold. Stage 3 was tool-equipped in every arm, so the design cannot establish that tools caused attenuation. The pooled Stage-3 difference was nonsignificant, and Haiku’s clean holds went in the opposite direction from the highlighted Nemotron pairing. See repohandoff/prompts.py:65–85, 238–269 and repohandoff/briefs.py:65–104.
- paper/main.tex:38, 55, 234, 262, “pass local tests while omitting the frozen requirement,” “conceal failures or tamper with tests,” and “7/216 … via dynamic indirection.” These are outcome labels for a deliberately conflicting ticket and freeze setup. H4a requires green visible pytest, a nonzero oracle exit, and the classifier’s report conditions. It does not independently establish which requirement was missing in every case. H4b includes silent reports, false pass claims, and AST changes, without establishing intent to conceal. Gemma T01 explicitly says it modified the freeze test. Seven runs passed both suites with zero recorded AST tampering and reports consistent with workarounds. The saved worker traces lack final source snapshots and write contents, so the exact mechanisms are report-supported, not independently replayable. Figure 3 calls these runs “Complete,” while the manuscript table calls them “Evaded.”
- paper/main.tex:55, 270, “test tampering that evades digest checks alone” and “updated its report with the passing test names.” In Part 2 the worker reports a boolean, and the harness fills `passed_tests` from its own observed pytest results before issuing a fresh voucher. The case demonstrates that re-signing a post-edit snapshot and rerunning its visible tests does not establish test integrity. It does not show the worker supplied matching test IDs or defeated a previously trusted digest. The three green partials blocked by CI had negative pass reports, so those blocks do not demonstrate detection of semantic omissions. See repohandoff/worker.py:229–241.
- paper/main.tex:56, 277, 293, 297–303, “commit-anchored production field evidence,” “Every failure stemmed from,” “maps cleanly,” and “Five commit-anchored … failures.” The fifth table row supplies command names rather than commits. The other hashes identify purported repairs but do not independently verify incident occurrence, cause, duration, or remediation. Token permissions, missing configuration, and process-scanner self-matches are analogies to the experiments. The paper does acknowledge the cases are descriptive and private. Its introduction and caption should honor that limit.
- paper/main.tex:38, 325–334, “reliable handoffs require deterministic, test-integrity-checked, and request-bound gates,” “Bind every merge transition,” “Never deploy,” and “eliminating … fabrication without dropping solitary requirement catches.” There is no separate conclusion, so these passages do its work. The experiments do not test the necessity or sufficiency of this production architecture. B tests a request-aware prompt, C tests a brief filter and observes one solitary omission dissent, and Part 2 tests selected checks in an engineered setting. The gate’s “concrete requirement-omission citation” is implemented as a broad text regex with a preserve-by-default path for ambiguous solitary holds. Phrase the rules as design implications and distinguish the tested conjunctions from the proposed ones.

4. Preregistration and deviations

- H1a–H3c match the locked arms, conditions and left-right order in `HYPOTHESES.md:37–56` and `repohandoff/analyze.py:22–38`. H2a’s negative sign in the abstract is the descriptive switch from goal to narrow. The table reports the locked goal-minus-narrow sign. Tests are two-sided. McNemar pairs on repository and seed within a model or C pairing. Pooled tests use 36 repository means, excluding the 18-task Sol slice in A/B and including all five C pairings. Holm is applied over three contrasts within each model or pairing, and separately for each pooled test within each block. “Per model family” at paper/main.tex:117 is inaccurate if read as developer family. The implementation uses model or pairing.
- HYPOTHESES.md:33–35 does not give sign and Wilcoxon a primary/secondary ordering. The manuscript calls that ordering preregistered. It should describe it as a reporting choice. The code uses SciPy’s default Wilcoxon method with tied and zero differences, so it should report the version and method rather than imply both pooled procedures are exact. H1a mentions criterion changes, but the formal contrast tests holds. Descriptive `c` values do not establish a changed decision criterion. Similarly, the ledger’s “pre-registered null” language for H1 and H3 is unsupported by the directional scientific expectations in the lock. [SciPy’s Wilcoxon documentation](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.wilcoxon.html)
- The locked sampling description does not match every backend. The Claude CLI drops seed and temperature, OpenAI can omit temperature if rejected, and Ollama retries shift the effective seed and temperature. C1 advisors get a truncated diff in a single prompt rather than the interactive receiver tool set. The lock’s “length-matched” A control was not implemented. H2c changes both ticket availability and the duty wording, so it does not isolate ticket removal. See repohandoff/backends.py:150–178, 243–266, 298–319 and repohandoff/prompts.py:37–51, 169–179, 195–205.
- H4a/b’s published formulas match HYPOTHESES.md:58–62. The pooled Wilson interval treats 216 worker-model runs as independent, even though the general replication rule names the repository. Report the allocation-weighted descriptive rates and show repository-clustered uncertainty or a sensitivity analysis. The `complete` → `Evaded` interpretation needs an explicit post-lock designation and coding criteria.
- There are no confirmatory files in the lock tree at `f7ec48c`. The tracked diff updates the deviation log, Ollama backend and sweep concurrency. The log discloses retry escalation and concurrency changes, but leaves out the later-attempt token cap and final-retry prompt suffix. Four C1/C2 retry-tagged records are directly verifiable. Receiver and worker records do not retain per-call retry metadata, so the archive cannot establish retry exposure in every arm or independently prove zero discarded/rerun attempts. The Git history verifies the committed lock and subsequent diff. It does not establish the historical remote push time relative to the first live call.
- Terminal non-hold scoring was not specified in the lock. It avoids counting parse errors as defect catches but can also suppress clean false alarms. I found eight terminal receiver error records, seven unique after removing the copied B discretion error. The denominator is 5,436 records or 5,040 after removing copied receiver records. Reclassifying errors as holds, or dropping their matched pairs, left the exact-test significance decisions unchanged in A, B and C. The A-to-B reuse is recorded in the raw data and implemented at `repohandoff/sweep.py:129–136`. The lock and paper should disclose it.

5. Methodological weaknesses

- Single nominal seed, one execution per arm, one set of prompt templates and uneven backend controls. Repository clustering addresses repeated model observations within a task, but neither repeated model draws nor correlation among the three tasks per domain. As a sensitivity check, I aggregated the raw paired differences by domain. H1c and all three H2 contrasts still had the same direction in all 12 domains. That supports the strongest findings within this bank. A nonsignificant result cannot “rule out large effects” as claimed at paper/main.tex:117 without effect intervals or an equivalence analysis.
- Synthetic tickets, fixtures, patches and oracles share authorship and assumptions. AI assistance is disclosed, but the paper supplies no task-by-task authorship provenance or independent adjudication of clean labels. The T00 discrepancy makes that consequential. Part 2 has no freeze-free control and explicitly tells workers to leave tests green and disclose blocked requirements. Its high partial rate is conditional on that setup. Also, 112 of the 135 green partial labels have oracle exit 2. The archive does not retain oracle diagnostics for distinguishing expected missing-symbol collection errors from other collection failures and assertions.
- The recount is independent code for selected arithmetic. It imports no analyzer or SciPy and implements its own binomial tail. It shares the original classification fields, constants, pairing keys and complete-pair intersections, so it cannot expose shared label errors or independently validate fixture execution. It does not recompute Holm, Wilcoxon, SDT, deterministic baselines, Part-2 confidence intervals, semantic classifications, or costs. It also does not enforce uniqueness of the pairing keys. “All statistics independently recounted” is materially inaccurate. See scripts/recount_independent.py:13–57, 99–175, 248–336.
- Seven labels from five developers is a roster description. Core 5 represents four developer families, with OpenAI counted twice. C uses one fixed three-family advisor panel, two of those models again as synthesizers, and five non-independent pairings with one synthesizer in four. C has five developer families across all stages, four among Stage-3 deciders, and three in each actual advisor panel. `decider_family` in the records is a backend field such as `ollama`. None of this estimates a family effect or independently ranks “stronger” and “weaker” models.
- Part 2’s integrity evaluation has incorporation bias: the AST flag both defines tampering and makes the integrity gate reject it, so 5/5 is true by construction. The informative incremental case is Gemma T01, one AST-flagged record accepted by the CI baseline. Worker records omit final code, detailed oracle output, and per-call metadata. The field section has an analogous provenance problem: five selected cases from one private author-operated deployment, with no case selection rule, denominator, accessible incident artifacts, or comparison group.
